# 코드베이스 리서치

여러 파일에 걸친 작업을 시작하기 전에, 코드베이스가 **지금 어떻게 되어 있는지**를
근거가 붙은 문서 하나로 남긴다. 이 문서는 이어지는 설계·계획·구현 세션의 입력이 된다.

## 왜 이 단계를 따로 두는가

나쁜 코드 한 줄은 한 줄이다. 나쁜 계획 한 줄은 수백 줄의 나쁜 코드가 된다.
그리고 코드베이스에 대한 **오해 한 줄은 수천 줄**이 된다 — 잘못된 위치를 고치고,
잘못된 관례를 따르고, 존재하지 않는 계층을 가정하게 만들기 때문이다.

그래서 리서치는 별도 단계이고, 사람이 가장 먼저 검토해야 하는 산출물이다.
여기서 틀리면 뒤가 전부 틀린다. 사용자가 리서치 결과를 읽고 **버리는** 것은
정상적인 진행이지 실패가 아니다.

## 절대 규칙 — 문서화만 한다

이 스킬이 도는 동안에는 다음을 하지 않는다.

- 개선 제안, 리팩터·최적화 권고
- 근본 원인 분석 (사용자가 명시적으로 요청한 경우 제외)
- 코드 품질·아키텍처 결정에 대한 비평
- "이건 문제가 있어 보인다" 류의 판단

**존재하는 것이 무엇이고, 어디에 있고, 어떻게 동작하고, 무엇과 맞물리는지만** 쓴다.

이유가 있다. 리서치 문서에 제안이 섞이면 그 제안이 검증되지 않은 채로 설계 단계의
전제가 되고, 계획을 거쳐 코드까지 증폭된다. 사실과 의견을 한 문서에 섞으면
사람이 검토할 때 둘을 분리하는 비용이 조사 자체보다 커진다.
개선 아이디어가 떠오르면 문서 맨 아래 `## 미해결 질문` 에 **질문 형태로만** 남긴다.

같은 규칙을 서브에이전트에게도 그대로 전달해야 한다. 상위 지시만 걸어두면
새 컨텍스트에서 시작하는 서브에이전트에게는 적용되지 않는다.

## 진행 절차

### 1. 언급된 파일을 먼저 전부 읽는다

사용자가 파일·티켓·로그를 지목했다면 **서브에이전트를 띄우기 전에** 메인 컨텍스트에서
`limit`/`offset` 없이 전부 읽는다. 질문을 제대로 쪼개려면 원문을 알아야 한다.

### 2. 질문을 3~5개 리서치 영역으로 쪼갠다

"인증이 어떻게 동작하나" 는 그대로 조사할 수 없다. 진입점 / 토큰 발급·검증 / 세션 저장소 /
미들웨어 배선 / 기존 테스트 같은 식으로 나눈다.
쪼갠 결과를 사용자에게 한 줄씩 보여주고 시작한다 — 방향이 어긋났으면 지금 잡는 게 가장 싸다.

### 3. 탐색 서브에이전트를 병렬로 띄운다

서브에이전트를 쓰는 이유는 역할 분담이 아니라 **컨텍스트 통제**다.
파일 탐색과 코드 읽기는 컨텍스트를 가장 많이 먹는 작업이고, 그 소음을 별도 컨텍스트에
가둬야 메인 세션이 종합에 집중할 수 있다.

세 가지 역할로 나눠 동시에 띄운다.

| 역할 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 위치 찾기 | 관련 파일·디렉터리를 용도별로 분류해 경로만 반환 | 파일을 열어 읽지 않는다 |
| 동작 분석 | 지목된 코드의 흐름을 `file:line` 으로 추적해 설명 | 품질을 평가하지 않는다 |
| 유사 패턴 찾기 | 저장소 안의 비슷한 기능이 어떻게 구현돼 있는지 실제 예시 수집 | 어느 쪽이 낫다고 말하지 않는다 |

역할별 프롬프트 문안은 `references/subagent-prompts.md` 에 있다. 그대로 복사해 쓰고
조사 대상만 바꾼다. 특히 위치 찾기 역할에 "읽지 말라" 를 빼면 안 된다 — 읽을 수 있으면 읽고,
그러면 요약이 길어져 서브에이전트를 쓴 이유가 사라진다.

### 4. 전부 끝날 때까지 기다린 뒤 종합한다

일부 결과만 가지고 문서를 쓰기 시작하지 않는다. 종합할 때:

- 실제 코드에서 나온 결과가 1차 진실이다. 기존 `thoughts/` 문서는 보조 사료로만 쓴다
- 컴포넌트 사이의 연결을 명시한다. 각 부품 설명만 나열된 문서는 지도가 아니다
- 서브에이전트 결과가 이상하면 그대로 받아쓰지 말고 해당 파일을 직접 열어 확인한다

### 5. 메타데이터를 수집하고 문서를 쓴다

`references/output-format.md` 의 템플릿을 따른다. 순서가 중요하다 —
메타데이터를 먼저 수집하고 그다음에 문서를 쓴다.

### 6. 요약을 제시한다

문서 경로와 함께, 사용자가 바로 이동할 수 있는 핵심 `file:line` 몇 개를 짚어준다.
그리고 이 리서치가 맞는지 확인해달라고 요청한다.

후속 질문이 오면 **새 문서를 만들지 않는다.** 같은 문서에
`## 후속 리서치 [YYYY-MM-DD HH:mm]` 섹션을 덧붙이고 프론트매터의 `last_updated` 를 갱신한다.
한 주제에 대한 진실은 한 파일에 모여 있어야 한다.

## 공통 규약

- 산출물은 `thoughts/research/YYYY-MM-DD-HHmm-topic.md` 에 쓴다. 하루에 여러 번 돌리는 것을 전제로 시·분까지 붙인다
- 문서 상단에 YAML 프론트매터를 둔다: `date`, `git_commit`, `branch`, `repository`, `topic`, `tags`, `status`
- 메타데이터는 저장소에 스크립트를 심지 않고 이 네 줄로 직접 수집한다

  ```bash
  date -Iseconds
  git rev-parse HEAD
  git branch --show-current
  basename "$(git rev-parse --show-toplevel)"
  ```

- 코드를 가리킬 때는 반드시 `file:line` 형식으로 쓴다. 경로만 적힌 문서는 며칠 뒤 쓸모가 없어진다
- 사용자가 언급한 파일은 부분 읽기 없이 전부 읽는다. 앞부분만 읽고 세운 전제가 뒤 단계 전체를 오염시킨다
- 플레이스홀더가 남은 문서는 쓰지 않는다
- 다음 단계(`design-spec`)는 새 세션에서 시작하도록 안내한다. 이 문서가 컨텍스트 압축본 역할을 한다

## 이 스킬을 쓰지 않아야 할 때

파일 하나를 열면 답이 나오는 질문, 이미 재현 방법이 명확한 버그, 문구 수정.
이런 작업에 리서치 문서를 만드는 것은 순수한 낭비다. 바로 답하거나 바로 고친다.

# 탐색 서브에이전트 프롬프트

세 역할을 **동시에** 띄운다. 조사 대상만 바꿔 그대로 복사해 쓴다.
각 프롬프트에 "문서화만 한다" 조항이 포함돼 있는 것은 실수가 아니다 —
서브에이전트는 새 컨텍스트에서 시작하므로 상위 지시가 전달되지 않는다.

## 역할 1 — 위치 찾기

```
[조사 대상] 과 관련된 파일이 이 저장소 어디에 있는지 찾아라.

너의 일은 위치를 찾는 것이다. 파일을 열어 내용을 읽지 마라.
파일명, 디렉터리 구조, 그리고 검색 결과의 매치 위치만으로 판단한다.
읽기 시작하면 반환할 내용이 길어지고, 그러면 이 작업을 분리한 이유가 사라진다.

코드베이스를 있는 그대로 기록한다. 개선 제안, 구조에 대한 평가,
"이렇게 나뉜 게 이상하다" 같은 판단은 쓰지 않는다.

이 형식으로 반환하라:

## 구현 파일
- `path/to/file.ext` — 이 파일이 담당하는 것으로 보이는 역할

## 테스트 파일
- ...

## 설정 / 배선
- ...

## 관련 디렉터리
- `path/to/dir/` — 관련 파일 N개 포함

## 진입점
- `path/to/entry.ext:12` — 이 모듈이 처음 호출되는 지점
```

## 역할 2 — 동작 분석

```
[대상 파일 또는 기능] 이 어떻게 동작하는지 분석하라.

진입점에서 시작해 호출 경로를 따라가면서 데이터가 어떻게 변형되는지 추적한다.
필요한 파일은 부분 읽기 없이 전부 읽어라.

모든 설명에 `file:line` 을 붙여라. 줄 번호 없는 설명은 검증할 수 없다.

코드가 지금 어떻게 되어 있는지만 기술한다. 버그를 찾거나, 성능·보안 문제를 지적하거나,
더 나은 방법을 제안하지 마라. 그건 이 작업의 범위가 아니다.

이 형식으로 반환하라:

## 진입점
## 호출 흐름
   1. `file.ext:31` — 무엇을 하는지
   2. `other.ext:88` — 다음으로 무엇이 일어나는지
## 데이터 변형
## 외부 의존성
## 관찰된 에러 처리 방식
```

## 역할 3 — 유사 패턴 찾기

```
이 저장소에서 [비슷한 기능] 이 이미 어떻게 구현돼 있는지 실제 예시를 찾아라.

목적은 새로 만들 것이 기존 관례를 따르게 하는 것이다.
실제로 존재하는 코드를 인용하고, 어느 쪽이 더 낫다는 평가는 하지 마라.

각 예시마다 이 형식으로 반환하라:

### [예시 이름]
- 위치: `path/to/file.ext:120-158`
- 하는 일: [한 줄]
- 눈에 띄는 관례: [에러 처리 방식, 이름 규칙, 테스트 배치 등]
- 실제 코드:
  ```
  [핵심 부분만 짧게]
  ```
```

## 결과를 받은 뒤

- 세 결과가 서로 어긋나면 해당 파일을 직접 열어 확인한다. 서브에이전트 결과를 그대로 받아쓰지 않는다
- 한 역할의 결과가 비어 있으면 검색어를 바꿔 다시 띄우는 편이, 없는 것으로 결론짓는 것보다 낫다

## 성공 기준을 나누는 방법

두 종류의 차이는 **에이전트가 혼자 확인할 수 있는가**이다.

### 자동 검증

그대로 실행 가능한 명령 문자열로 쓴다. 구현 에이전트가 복사해 붙여넣을 수 있어야 한다.

```markdown
- [ ] 마이그레이션 적용: `make migrate`
- [ ] 단위 테스트 통과: `go test ./internal/auth/...`
- [ ] 타입 체크 통과: `npm run typecheck`
- [ ] 엔드포인트 응답: `curl -sf localhost:8080/healthz`
```

`테스트를 실행한다` 처럼 명령이 없는 항목은 자동 검증이 아니다.
프로젝트에 `make` 타깃이 있으면 그것을 쓴다 — 명령이 바뀌어도 계획이 낡지 않는다.

### 수동 검증

사람이 봐야 하는 것. 결과가 아니라 **절차**를 쓴다.

```markdown
- [ ] 로그인 화면에서 SSO 버튼이 보이고, 눌렀을 때 IdP 로 이동한다
- [ ] 항목 1000개 이상에서 목록 로딩이 체감상 느리지 않다
- [ ] 세션 만료 후 재접속하면 로그인 화면으로 돌아간다
```

수동 항목은 사용자가 확인해주기 전까지 체크하지 않는다.

## 자주 나오는 실수

- **수평 계획** — 페이즈가 마이그레이션 / 서비스 / API / 프론트로 나뉘어 있으면 다시 쪼갠다
- **"이 페이즈가 끝나면" 을 못 쓰는 페이즈** — 확인할 수 있는 것이 없다는 뜻이다
- **모호한 변경 지시** — "인증 로직을 수정한다" 는 계획이 아니다. 파일과 지점을 쓴다
- **미해결 질문을 남기기** — 구현 에이전트가 그 자리에서 아무거나 고른다
- **`하지 않을 것` 생략** — 범위가 새는 것을 막을 방법이 없어진다

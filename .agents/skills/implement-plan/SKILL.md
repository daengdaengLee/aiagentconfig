# 계획 실행

`thoughts/plans/` 의 승인된 계획을 페이즈 단위로 실행한다.

## 이 단계는 기계적이어야 한다

앞 단계(리서치·설계·계획)가 두꺼운 이유는 여기가 얇아지기 위해서다.
**구현이 창의적으로 느껴진다면 앞 단계에 빠진 것이 있다는 신호다.**
그럴 때 즉흥적으로 채우지 말고 멈춰서 그 사실을 알린다. 되돌아가는 편이 싸다.

## 시작하기

1. 계획 문서를 **전부** 읽는다. 기존 체크마크(`- [x]`)를 확인해 어디까지 됐는지 파악한다
2. 계획이 참조하는 설계·리서치 문서와 코드 파일을 부분 읽기 없이 읽는다
3. 진행 상황을 추적할 할 일 목록을 만든다
4. 계획 경로가 주어지지 않았으면 물어본다. 최근 계획은 `ls -lt thoughts/plans/ | head` 로 찾을 수 있다

## 계획을 믿는다 — 이미 문서화된 것을 다시 찾지 않는다

계획에 정확한 파일 경로, 지울 코드 블록, 바꿀 시그니처가 적혀 있으면 **그대로 쓴다.**
이미 문서화된 것을 "다시 확인" 하려고 검색하지 않는다.

검색은 두 경우에만 한다.

- 계획이 애매해서 그대로는 실행할 수 없을 때
- 변경이 빠짐없이 반영됐는지 확인할 때 (예: 어떤 심볼의 남은 참조 찾기)

이건 신뢰의 문제가 아니라 컨텍스트 예산의 문제다. 계획을 다시 검증하기 시작하면
구현 세션이 리서치 세션이 되고, 정작 코드를 쓸 여유가 남지 않는다.

## 한 번에 슬라이스 1~3개

각 페이즈를 끝낼 때마다 순서대로:

1. **자동 검증을 실행한다** — 계획의 "자동 검증" 항목에 적힌 명령을 그대로 돌린다.
   실패하면 다음 페이즈로 넘어가기 전에 고친다
2. **계획 파일의 체크박스를 갱신한다** — 자동 검증 항목만. 계획 문서가 진행 상태를 담는
   체크포인트이므로, 컨텍스트가 가득 차 세션을 새로 시작해도 여기서 이어받을 수 있다
3. **변경분을 사람에게 보여준다** — 무엇이 어떻게 바뀌었는지 요약하고, 필요하면 diff 를 제시한다
4. **멈추고 수동 검증을 요청한다**

```
Phase [N] 완료 — 수동 확인이 필요합니다

자동 검증 통과:
- [통과한 항목들]

변경 내용:
- `path/to/file.ext:31-58` — [무엇을 바꿨는지]

계획의 수동 검증 항목을 확인해 주세요:
- [계획에 적힌 수동 항목들]

확인되면 Phase [N+1] 로 진행하겠습니다.
```

**수동 항목은 사용자가 확인해주기 전까지 체크하지 않는다.**
여러 페이즈를 연속으로 진행하라는 지시가 있으면 마지막 페이즈까지 정지를 건너뛴다.
그런 지시가 없으면 **기본값은 한 페이즈**다.

## 사람이 코드를 읽는 지점을 남긴다

3번을 형식적으로 하지 않는다. 100~200줄 단위로 방향을 다시 잡는 것이,
2000줄을 쌓아놓고 무엇이 깨졌는지 찾는 것보다 압도적으로 싸다.

특히 새로 만든 파일, 기존 코드에 끼어드는 지점, 계획에 없던 판단을 내린 곳은
사용자가 보고 넘어가게 한다. 지금 방향을 트는 비용은 나중의 몇 분의 일이다.

## 계획과 현실이 어긋날 때

계획은 신중하게 만들어졌지만 현실은 지저분하다. 계획이 쓰인 뒤 코드가 바뀌었을 수도 있다.

어긋나는 지점을 발견하면 **멈춘다.** 추측으로 메우지 않는다.

```
Phase [N] 문제:
Expected: [계획이 말하는 것]
Found: [실제 상황]
Why this matters: [이것이 왜 문제인지]

어떻게 진행할까요?
```

작은 차이 — 변수 이름, 계획에 없던 사소한 헬퍼 — 는 판단해서 진행하고 결과 보고에 적는다.
구조나 범위가 달라지는 차이는 반드시 물어본다.

## 서브에이전트는 아껴 쓴다

구현 단계에서 서브에이전트를 쓰는 것은 표적 디버깅이나 낯선 영역을 잠깐 훑을 때 정도다.
계획이 이미 어디를 어떻게 고칠지 말해주고 있으므로 탐색할 것이 많지 않아야 정상이다.
서브에이전트를 자주 띄우게 된다면 계획이 충분히 구체적이지 않다는 신호다.

## 이어서 작업할 때

계획에 체크마크가 있으면 완료된 작업을 신뢰하고 **첫 미완료 항목부터** 시작한다.
이미 된 것을 다시 검증하지 않는다 — 무언가 이상해 보일 때만 확인한다.

## 마친 뒤

- 계획의 모든 페이즈가 끝나면 전체 자동 검증을 한 번 더 돌린다
- 계획에서 벗어난 부분, 계획에 없던 판단을 내린 지점을 목록으로 보고한다
- 계획 문서의 `status` 프론트매터를 `complete` 로 갱신한다

## 공통 규약

- 입력은 `thoughts/plans/YYYY-MM-DD-HHmm-description.md`
- 계획과 계획이 참조하는 문서는 부분 읽기 없이 전부 읽는다
- 코드를 가리킬 때는 `file:line` 형식으로 쓴다
- 진행 상태는 계획 파일에 기록한다. 세션이 바뀌어도 그 파일 하나로 이어받을 수 있어야 한다

# 설계 스펙

코드를 쓰기 전에, 사람이 검토할 수 있는 설계 문서를 만든다.
여기서 내리는 결정들은 **어차피 내려야 하는 결정**이다. 다만 설계 단계에서 내리면
문단 몇 개를 고치면 되고, 코드 리뷰 단계에서 내리면 수백 줄을 되돌려야 한다.

## 0. 먼저 게이트 — 이 작업이 이 절차를 받을 만한가

모든 작업에 설계 문서가 필요하지는 않다. 들이는 노력과 나중에 겪을 고통의 관계는
대략 이렇다.

```
기대 고통 = P(고쳐야 할 확률) × 고치는 데 드는 고통
```

두 문장짜리 요청을 그냥 던지면 재작업 확률이 대략 절반, 반나절 걸려 정밀한 스펙을 쓰면
10% 근처, 전부 손으로 쓰면 0%지만 얻는 것도 없다. 중요한 건 이 곡선이 **초반에 급격히
떨어진다**는 점이다 — 기대 고통의 8할은 처음 몇 분에 사라진다.
10분이면 8할을 없앨 수 있는 작업에 여섯 시간짜리 설계를 붙이는 것은 손해다.

작업을 셋 중 하나로 분류하고 사용자에게 알린다.

| 규모 | 판단 기준 | 이 스킬의 진행 방식 |
| --- | --- | --- |
| 작음 | 파일 한두 개, 명백한 버그, 문구·설정 변경, 되돌리기 쉬움 | **설계 문서를 만들지 않는다.** 바로 구현한다 |
| 중간 | 여러 파일에 걸치지만 접근 방식이 하나로 보임 | 세 단계를 **한 문서에** 합쳐 짧게 쓴다 |
| 큼 | 새 기능, 대규모 리팩터, 마이그레이션, 여러 계층을 건드림 | 세 단계를 순서대로, 각각 사람과 왕복하며 진행 |

큰 작업이라도 성격에 따라 단계를 건너뛴다. 예를 들어 순수한 내부 리팩터는
사용자가 보는 것이 바뀌지 않으므로 프로덕트 요구사항 단계를 생략한다.

게이트 판단이 애매하면 **사용자에게 물어본다.** 판단을 대신 내리는 것보다 한 번 묻는 게 싸다.

## 진행 원칙

세 단계 모두 이 두 가지를 지킨다.

**회의적으로 진행한다.** 사용자가 "그건 저기 있어" 라고 정정해줘도 그대로 받아들이지 않는다.
해당 파일을 직접 열어 확인한 뒤 진행한다. 사람도 자기 코드베이스를 잘못 기억한다.
잘못된 전제를 검증 없이 받으면 설계 전체가 그 위에 세워진다.

**미해결 질문을 남긴 채 문서를 완성하지 않는다.** 질문이 생기면 멈추고 조사하거나 물어본다.
"이 부분은 구현하면서 정하자" 라고 적힌 설계 문서는, 구현 에이전트가 그 자리에서
아무거나 고르게 만든다. 답할 수 없는 질문은 사용자에게 던지고 기다린다.

리서치 문서(`thoughts/research/`)가 있으면 시작 전에 전부 읽는다. 없는데 코드베이스가
낯설면 먼저 `codebase-research` 를 돌리자고 제안한다.

## 1단계 — 프로덕트 요구사항

**무엇을 왜 만드는지**를 고정한다. 두 가지만 확실히 한다.

1. **문제** — 사용자 언어로 쓴 실제 불편. 기술 용어가 아니라 사용자가 겪는 것.
2. **성공의 정의** — 출시한 뒤 무엇을 읽고 "이걸 만들 만했다" 고 판단할 것인가.
   이상적으로는 "이 작업을 더 짧은 시간에 할 수 있다" 같은 사용자 결과다.
   때로는 에러율이나 지연 시간, 때로는 그냥 "이것에 대한 문의가 멈춘다" 여도 된다.

기술 얘기로 흐르는 자신을 발견하면, 적어두고 다음 단계로 넘긴다.

화면이 바뀌는 작업이면 **설명하지 말고 목업을 만든다.** 거친 HTML 한 장이
세 문단으로 끌 논쟁을 끝낸다. 상세는 `references/product-requirements.md`.

## 2단계 — 시스템 아키텍처

서비스·엔드포인트·스키마·큐·저장소가 서로 어떻게 대화하는지 맞춘다.
여기서는 사람과 에이전트 사이의 대역폭을 최대로 올리는 게 목적이므로 시각화를 적극적으로 쓴다 —
시퀀스 다이어그램, 엔드포인트 계약, 데이터 모델과 새로 생기는 쿼리 형태.

주의할 점이 하나 있다. 다이어그램은 **맞췄다는 착각**을 주기 쉽다.
그림은 예쁘게 나왔는데 정작 함수 시그니처는 아무도 합의하지 않은 상태가 자주 생긴다.
그래서 이 단계만으로는 좋은 코드가 나오지 않는다. 다음 단계가 필요하다.

상세와 템플릿은 `references/system-architecture.md`.

## 3단계 — 프로그램 설계

이 스킬의 무게중심이다. 아키텍처가 정해지면 모델이 알아서 잘 만들 거라고 넘어가기 쉬운데,
그렇게 하면 결과가 마음에 들지 않는 경우가 많다.

아키텍처보다 한 층 아래, **코드의 모양**을 먼저 정한다 — 타입, 메서드 시그니처,
파일 배치, 호출 스택. 세 가지 가벼운 시각화를 쓴다.

- **콜스택 트리** — 제어 흐름이 바뀌는 부분은 diff 문법으로
- **파일 트리 diff** — 어떤 파일이 새로 생기고 어떤 파일이 바뀌는지
- **핵심 타입과 시그니처** — 아키텍처 문서에 넣기엔 너무 내부적이지만 에이전트가 틀리기 쉬운 것들

무거운 다이어그램 언어보다 **의사코드 diff** 가 낫다. 읽는 데 드는 비용이 훨씬 적고,
틀린 부분을 지적하기도 쉽다. 상세와 예시는 `references/program-design.md`.

모델이 초안을 만들고 사람이 반박하는 방식으로 진행한다. 오래 걸리지 않는다.
그리고 여기서 정하는 것 하나하나가, 안 정하면 코드 리뷰 때 — 마음을 바꾸기 가장 비싼 시점에 —
정하게 될 것들이다.

## 마무리

문서를 쓴 뒤 사용자에게 검토를 요청한다. 이때 **PR 을 리뷰할 사람**에게 이 설계 문서를
먼저 보여주는 것이 리뷰 시간을 줄이는 가장 확실한 방법이라는 점을 함께 안내한다.

설계가 확정되면 다음은 `slice-plan` 이다. 새 세션에서 시작하도록 안내한다.

## 공통 규약

- 산출물은 `thoughts/design/YYYY-MM-DD-HHmm-topic.md` 에 쓴다. 중간 규모면 세 단계를 한 문서에 합친다
- 문서 상단에 YAML 프론트매터를 둔다: `date`, `git_commit`, `branch`, `repository`, `topic`, `tags`, `status`
- 메타데이터는 저장소에 스크립트를 심지 않고 이 네 줄로 직접 수집한다

  ```bash
  date -Iseconds
  git rev-parse HEAD
  git branch --show-current
  basename "$(git rev-parse --show-toplevel)"
  ```

- 코드를 가리킬 때는 반드시 `file:line` 형식으로 쓴다
- 사용자가 언급한 파일과 기존 리서치 문서는 부분 읽기 없이 전부 읽는다
- 플레이스홀더가 남은 문서는 쓰지 않는다
- 다음 단계(`slice-plan`)는 새 세션에서 시작하도록 안내한다. 이 문서가 컨텍스트 압축본 역할을 한다

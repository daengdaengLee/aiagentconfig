# 프로그램 설계

## 목적

아키텍처보다 한 층 아래, **코드의 모양**을 코드를 쓰기 전에 정한다 —
타입, 메서드 시그니처, 파일 배치, 호출 스택.

아키텍처가 정해지면 모델이 알아서 잘 만들 거라고 넘어가기 쉽다. 그렇게 해도 돌아가긴 하지만
결과물이 마음에 들지 않는 경우가 많고, 그때는 이미 되돌리기 비싼 상태다.

여기서 정하는 것 하나하나가, 안 정하면 **코드 리뷰 때 정하게 될 것들**이다.
같은 결정을 가장 싼 시점에 내리는 것이 이 단계의 전부다.

## 형식: 무거운 다이어그램보다 의사코드 diff

다이어그램 언어로 이 층위를 표현하면 읽기 힘들고 쓰는 것도 지친다.
읽는 비용이 낮고 틀린 부분을 바로 짚을 수 있는 **가벼운 의사코드**를 쓴다.

모델이 초안을 만들고 사람이 반박하는 방식으로 진행한다. 오래 걸리지 않는다.

## 세 가지 산출물

### 1. 콜스택 트리

제어 흐름이나 오케스트레이션이 바뀌는 작업이면 반드시 만든다.
바뀌는 부분은 diff 문법으로 표시해서, 무엇이 새로 끼어들고 무엇이 빠지는지 한눈에 보이게 한다.

```diff
 entrypoint
   runCommand
+    handleCreateResource
+      ResourceClient.create(input)
+        POST /resources
+      renderResult
-    legacyCreateFlow
```

이 트리를 그리다 보면 "이 호출이 여기 있는 게 맞나" 가 드러난다.
드러나지 않으면 계층이 하나 빠졌거나 너무 얕게 그린 것이다.

### 2. 파일 트리 diff

어떤 파일이 새로 생기고 어떤 파일이 바뀌는지. 코드베이스의 배치 감각을 유지하는 장치다.

```diff
 src
 └── resource
+    ├── resource-client.ts      # NEW - API 계약 호출을 감싼다
+    ├── resource-client.test.ts # NEW - 요청/응답 매핑을 검증한다
~    └── resource-route.ts       # MODIFIED - 생성 액션을 UI 에 배선한다
```

새 파일에는 한 줄 설명을 붙인다. 설명을 못 쓰겠으면 그 파일이 필요한지 다시 생각한다.

### 3. 핵심 타입과 시그니처

아키텍처 문서에 넣기엔 너무 내부적이지만, 에이전트가 틀리기 쉬운 것들.
특히 **경계 조건이 타입에 드러나는지**를 본다.

```ts
interface Item {
  id: ItemId
  parentId: ItemId | null
  // ...
}

interface Cursor {
  position: ItemId
  direction: 'up' | 'down'
  // ...
}

resolveTarget(items: Item[], cursor: Cursor) -> ItemId | null
```

`null` 이 반환될 수 있는지, 실패를 예외로 던지는지 값으로 반환하는지,
컬렉션이 비어 있을 수 있는지 — 이런 것들이 여기서 정해지지 않으면
구현 에이전트가 그 자리에서 아무거나 고른다.

## 문서 템플릿

```markdown
## 프로그램 설계

### 콜스택

[diff 문법 콜스택 트리]

### 파일 배치

[diff 문법 파일 트리]

### 타입과 시그니처

[새로 생기거나 바뀌는 핵심 타입·함수]

### 따를 기존 관례

[이 저장소에서 이미 쓰이는 패턴 중 이번 코드가 따라야 할 것.
`file:line` 으로 실제 예시를 가리킨다. 리서치 단계의 "유사 패턴" 결과를 여기에 쓴다.]

- 에러 감싸기: `internal/store/user.go:88` 방식을 따른다
- 테스트 배치: 같은 디렉터리에 `*_test.go`

### 결정한 것

[논의 끝에 정한 것들. 특히 갈렸던 지점.]

- 실패를 예외 대신 `(값, 에러)` 로 반환한다 — 저장소 전체가 그렇게 되어 있다
```

## 얼마나 깊이 들어갈 것인가

전부를 설계하지 않는다. **에이전트가 틀리면 비싼 것**만 정한다.

정해야 하는 것:
- 여러 파일이 공유하는 타입과 인터페이스
- 실패·경계 조건의 표현 방식 (`null` 허용, 에러 반환 형태)
- 새로 생기는 파일의 위치와 책임
- 기존 코드에 끼어드는 지점

정하지 않아도 되는 것:
- 함수 내부의 지역 변수와 루프
- 로그 문구
- 단순 위임 함수의 본문

## 자주 나오는 실수

- **너무 얕게 그리기** — 콜스택이 두 단계면 아무것도 결정하지 못한 것이다
- **전부 설계하기** — 구현 에이전트가 판단할 여지를 남긴다. 지치는 문서는 아무도 안 읽는다
- **기존 관례를 안 적기** — 새 코드가 저장소 안에서 혼자 다른 모양이 되는 가장 흔한 원인이다

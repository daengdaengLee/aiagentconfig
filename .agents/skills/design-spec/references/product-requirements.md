# 프로덕트 요구사항

## 목적

무엇을 왜 만드는지 고정한다. 두 문장짜리 요청이나 긴 음성 메모를
반쯤 구조화된 형태로 바꾸는 것이 이 단계의 일이다.

**에이전트가 의도를 잘못 이해하면 비싼 변경**에만 쓴다.
문구 수정, 일회성 스크립트, 재현이 명확한 버그에는 만들지 않는다.

## 두 가지만 확실히 한다

### 1. 문제

사용자 언어로 쓴다. 시스템 구조가 아니라 사람이 겪는 것을 쓴다.

- 좋음: "설정을 바꾸려면 매번 팀 채널에 요청하고 담당자를 기다려야 한다"
- 나쁨: "설정 API 에 PUT 엔드포인트가 없다"

두 번째 문장은 해결책이지 문제가 아니다. 해결책을 문제 자리에 쓰면
그 해결책 말고 다른 선택지를 검토할 기회가 사라진다.

### 2. 성공의 정의

**출시한 뒤 무엇을 읽고 판단할 것인가.** 미리 정해두지 않으면 나중에
"잘된 것 같다" 로 끝난다.

- 사용자 결과: "이 작업을 더 짧은 시간에 끝낸다", "온보딩 N단계에 더 빨리 도달한다"
- 낮은 층위 지표: 에러율, 지연 시간
- 가장 단순한 형태: "이것에 대한 문의가 멈춘다"

## 기술 얘기로 흐를 때

프로덕트와 기술 사이를 오가다 보면 자연스럽게 구현 얘기로 빠진다.
그럴 때는 **적어두고 다음 단계로 넘긴다.** 사용자가 실제로 겪는 것으로 돌아온다.

기술 결정이 프로덕트 결정을 막고 있다면 — 예를 들어 실현 가능한지 몰라서
무엇을 만들지 정할 수 없다면 — 지금까지 합의한 것만 문서에 남기고
아키텍처 단계로 넘어가거나, 실현 가능성을 확인하는 프로토타입을 먼저 만든다.

## 화면이 바뀌면 목업을 만든다

설명하지 말고 만든다. 거친 HTML 한 장이 세 문단으로 끌 논쟁을 끝낸다.

- 완성도를 높이지 않는다. 배치와 정보 구조가 보이면 충분하다
- 실제 문구를 넣는다. `Lorem ipsum` 이나 "제목 영역" 은 아무것도 결정하지 못한다
- 흐름이 있으면 화면 여러 장을 만든다. 화면 사이의 이동이 대부분의 논쟁이 일어나는 곳이다
- 파일은 설계 문서 옆에 둔다: `thoughts/design/YYYY-MM-DD-HHmm-topic.mockup.html`

워크플로처럼 단계가 있는 기능이면, 단계와 종료 조건을 JSON 이나 목록으로
먼저 적어두면 목업을 만들기 쉽다.

## 문서 템플릿

```markdown
## 프로덕트 요구사항

### 문제

[사용자가 지금 겪는 것. 사용자 언어로.]

### 누가 겪는가

[어떤 사용자인지. 전부라면 전부라고 쓴다.]

### 성공의 정의

출시 후 이것을 보고 판단한다:
- [읽을 수 있는 지표나 관찰 가능한 변화]

### 범위 밖

[이번에 하지 않는 것. 여기서 미리 잘라두면 뒤에서 논쟁이 줄어든다.]

### 목업

- `thoughts/design/2026-08-25-1512-sso.mockup.html` — 로그인 화면
- `thoughts/design/2026-08-25-1512-sso.settings.html` — 설정 화면

### 다음 단계로 넘긴 기술 메모

[여기서 떠올랐지만 아키텍처·프로그램 설계에서 다룰 것들]
```
